# How Wajo built Fo: a static reconstruction of the web client

Researched 2026-10-13 with REA (Reverse Engineer Anything, `rea-agents` 6.4.0) over the public, shipped JavaScript of wajo.ai, plus a line-by-line read of the same chunks after formatting. This note goes one level below [wajo-fo.md](wajo-fo.md): not what the product does, but how the client is wired, what the server sends it, and which policies are enforced in data rather than in a prompt. No code or assets were copied into this repo.

Everything here is split into three grades. **Observed** means a literal string, field name, constant or code path in the shipped bundle, with a file and line in the formatted copy. **Inferred** is our reading of observed code. **Unknown** is what the client cannot show because it lives on the server behind hashed server functions. Static analysis never observed execution; a code path present in the bundle is not proof that it runs.

The logged-in pages (`/fo`, `/fo/c/<session>`) redirect to `login.wajo.ai` from a clean environment, so nothing in this note comes from an authenticated page. ## 1. Architecture at a glance

**Observed.**

- Frontend: TanStack Start with React Query; Vite build; PostHog chunk ids injected into every chunk. Zod v4 is the `schemas-*.js` chunk (it is the library, not app schemas).
- Transport: the client never calls REST directly. Every data call is a server function `createServerFn({method}).middleware([apex]).handler(hash)` where the hash is a 64-hex id and the URL is `/_serverFn/<hash>` (`QueryClientProvider-BH1lnPzX.js:2098-2106, 2160-2215`). Requests carry `x-tsr-serverFn: true` and accept `application/x-tss-framed, application/x-ndjson, application/json`; GET payloads go as `?payload=<seroval JSON>` (`QueryClientProvider:1959-1976`). Responses can be seroval framed streams in which `ReadableStream` values are rehydrated (`QueryClientProvider:1737-1740, 2014-2030`). **Run and watch streams are therefore an HTTP response carrying a framed async stream, not EventSource and not WebSocket.**
- The server-side REST surface those functions call is still visible in two generated tables: the endpoint map (`endpoints-BTTBOVTN.js`, e.g. `SESSIONS.run = /v1/sessions/$sessionId:run`, `:runLongRunning`, `:watch`, `:stop`, `:checkRunnable`, `:openSidebar`, `/v1/sessions/$sessionId/events`) and the access table for `wajoai.agentnet.v1.AgentNetService` (224 methods with tier rules, catalogued in [wajo-fo-rpc-catalog.md](wajo-fo-rpc-catalog.md)).
- Error envelope: server function errors are strings matching `/^\[wajo_fn:(?<fn>[\w.]+)(?: status:(?<status>\d{3}))?\] ?/` and may carry the markers `[wajo_session_dead]` or `[wajo_user_gone]` (`serverFnError-Ez20loSU.js:20-37`, `session-dead-DX7WskgW.js:19-35`). A `user_gone` error reloads the page at most once per 30 s via sessionStorage key `wajo:session-recovered-at` (`session-recovery-04r9CA2j.js:20-42`).
- Dictation is Deepgram over WebSocket (`wss://api.deepgram.com/v1/listen?model=nova-3&encoding=linear16&…&interim_results=true&smart_format=true&endpointing=1200&utterance_end_ms=1500`, subprotocol `['bearer', token]`), with the token minted by the `scribe-token` server function (`attachment.type-*.js:180-190, 354, 630-641`). Text to speech is a server function taking `{text}`.
- Feature flags are a typed registry with dev defaults and optional zod payloads (`feature-flags-DXIZnl5t.js:30-68`): `foogle`, `devtools-modify`, `onboarding-sandbox`, `live-voice-chat`, `link-pay-rail`, `link-insights`, `telegram-link`, `fo-in-assistants`, `connect-x`, `hide-fo`, `welcome-fast-seed`, `starter-options-v2`, `inline-html-artifacts`, `fo-mascot-agent-state`, `prompt-sharing`, `release-stage-label`, `join-wajo-invite-code`, `pricing-section` (payload `proPriceUsd`, dev default 99), `plan-caps` (`tasks_per_day`, `turns_per_day` per tier), `authn-open-signup` (server evaluated), `plans-v2`, `marketing-pixels` (meta, tiktok, openai).
- MCP for an agent is gated client-side by `canUseMCP && (isPro || foInAssistants)` (`mcp-access-Co5S2iH0.js:20-22`).

**Inferred.** The split is deliberate: the browser holds UI state machines and optimistic caches; all policy (approval, spend, outreach, entitlements) is decided server-side and arrives as tool results, run events and attention items. The client's only "policy" is which card to draw for which status string.

## 2. A run, end to end

All of this is in `useComposerFlip` (UCF), which is the real run state machine; `chat` only renders it (`chat:3266`, UCF `Il` 3843-4040).

**Observed: starting a run.**

1. If there is no session yet, the client asks the server to mint one: server function `a5404fbd…690fc` with `{agentId, orgId}` returns a bare `sessionId`; the URL is rewritten in place to `/${handle}/c/${sessionId}` (UCF 819-826, 844-880). Until then the draft id is `draft:<useId()>` and transcript, access and runnable queries are local stubs (`chat.queries-DYXaVOBm.js:74-95`). Session ids are server-minted and bound to one agent, as the docs claim.
2. Optimistic UI: the user message is appended, an assistant placeholder `{id, role:'assistant', content:'', pending:true}` is added (UCF 782-783), and the recents row is patched to `latestRunStatus:'running'` (UCF 3938-3946).
3. The run stream opens with payload `{sessionId, text, fileRefIds, orgId, clientTime, geoLocation, acceptedSuggestionId?}` (UCF 2587-2611; server function `724407cb…94b5e0`, AQ 466). `clientTime` is `{timezone, utcOffsetMinutes}` (AQ 200-206). `geoLocation` is `{latitude, longitude, accuracyMeters, capturedAtUnixMs}` and is sent only when permission was already granted, capped at 12 s to acquire (`location-access-*.js:3-10, 141-143`). No agent id in the run payload: the session carries it.
4. Uploads go first, as FormData `{sessionId, orgId, file}` with retries at 2 s and 5 s inside a 30 s budget (UCF 379-399); limits are 10 files per message and 78,643,200 bytes total (UCF 916-931).
5. **Steering.** If the agent is busy and the new message is text-only, it is sent as a steer controller keyed `steer:<sessionId>:<clientTurnId>` with `userSteerState:'queued'`; a `started` frame can promote the steer to the primary run (UCF 3787-3826, 3878-3892). Attachments are refused mid-run: "Remove the attached files first: only text can be added to a running turn." (UCF 206-208, 239).
6. An answer to a `wait_for_user_input` tool is the same run endpoint with `fileRefIds:[]`, keyed `answer:<sessionId>`; the composer shows "Type your answer…" and "The agent is waiting on you before it can continue." (UCF 3687-3760; chat 1996-2033).

**Observed: stream events.** Handled in UCF 2654-2717 and 2574-2586: `started{runStatus?, cursor}`, `delta{text}`, `progress{status}`, `agent_state{state}`, `activity{line}`, `reset{runStatus?}`, `ping`, `user_message`, `steer_applied{steerEventIds}`, `steered{steerEventId}`, `error{message, runStatus?}`, `done{runStatus?}`, `tool_start{id, tool, displayLabel?, meta?, input?, rawInput?}`, `tool_end{id, isError, meta?, artifactIds?, callIds?, result?}`; `reconnecting` is client-synthesised (AQ 230-241). Terminal frames are `done | error | steered` (AQ 138, 217). Every frame may carry a `cursor` of the form `"<n>-<n>"` (UCF 2201-2210), which is what the watch endpoint resumes from.

**Observed: resilience constants.** Run open on HTTP 409 "session busy" backs off from 1.5 s doubling to 8 s within a 95 s deadline (AQ 109-115, 248-258); HTTP 429 is fatal (AQ 264). Watch backs off 1 s to 8 s within a 30 min deadline, giving up after 2 consecutive attempts with no progress (AQ 103-108, 265-283). Idle stall per attempt is 30 s (AQ 122); while a `wait_for_user_input` tool is running the idle window is 11 minutes, polled in 30 s slices (`workflows.calendar-*.js:21`). Error classes: `StreamIncompleteError`, `StreamStalledError{receivedAny}`, `StreamUnresolvedStartError`, `ChatStreamError{status}` (AQ 48-52, 117-135).

**Observed: two background observers the provider mounts (UCF 3471).**

- *Reconcile poll* (UCF 3124-3144, 2781-2811): re-fetches the transcript every 30 s (4 s during a credential-resume fast poll that self-expires after 55 s), doubling on failure up to 5 min (UCF 2132-2137, 2755-2763); skipped while the tab is hidden and forced on focus. It is skipped when a live stream controller exists, and when it does apply it merges the server transcript over local state, reporting `authoritative_reply_replaced_local_state` when they disagree (UCF 2879). A *wedge probe* aborts controllers older than 120 s (30 s if the tab was suspended) with reason `stale-turn-settle`, unless the server reports `activeRun === true` and the run is under 45 min old (UCF 2985-3024).
- *Passive session watch* (UCF 3182-3345): opens `watch` with `fromCursor:'$'`, idle window 45 s, retry 1 s doubling to 15 s with 50 to 100 % jitter, 500 ms after a clean close; any `session_dead`/`user_gone` ends the loop.

**Observed: failure copy.** "Something went wrong. Please try again." / "The connection dropped before the reply finished. Please resend." / "The agent didn't respond in time. Please try again." / "Fo is temporarily at capacity. Please try again." (UCF 2426-2433). Undelivered messages persist in sessionStorage under `fo:chat-undelivered:<key>` with resend and discard (UCF 1921, 4079-4121). Stop posts `{sessionId, dedupKey}` after aborting local controllers; on failure: "Couldn't stop the run – it's still going. Try Stop again." (UCF 4041-4071).

**Observed: telemetry.** One event, `fo_start_chat_turn_lifecycle`, with `lifecycle_kind` in `stream_start, attempt_open, attempt_frame, attempt_stall, reconnect_scheduled, reconnect_attempt, reconnect_outcome, abort, failure, terminal, wedge_probe, stop_pressed, session_watch_cut` (UCF 2288).

**Inferred: the client run states.** `idle` → (send) `busy` with a pending assistant bubble → frames mutate that bubble (`delta`, tool rows at `running`, `progress` text) → on `done` the bubble settles and running tools are dropped; on `error` the bubble becomes `role:'error'` with a Retry; on user stop the tail is `stopped:true`; on stream failure one of `wedge_settled`, `unresolved_start_armed` (recheck transcript after 30 s), `handed_off` (frames were received, so the reconcile poll takes over) or `settled` with one of the four messages above (UCF 4196-4208). A per-session `clientTurnId` latch lives 35 minutes (UCF 2251).

**Unknown.** Server-side run status enum beyond `running | stopped | failed | completed`; cursor semantics; how `backgroundWork`, `liveProgress` and `liveAgentState` are produced; the server's busy and dedup rules.

## 3. The message model and the step ledger

**Observed: transcript shape** (UCF 148-162, 2041-2070; chat 2068-2074): `{messages[], activeRun?, latestRunStatus?, latestRunAgentState?, latestRunDedupKey?, liveProgress?, liveAgentState?, liveActivity?, hiddenResumeTail?, credentialResumeMarkerId?, backgroundWork?:{statusLine, taskSummary?, eta?, startedAtMs?}, notFound?}`.

**Observed: message** (UCF 1934-1940, 2127-2131; CB 4738-4749): `{id, role:'user'|'assistant'|'system'|'error', content, pending?, progress?, activity?, agentState?, stopped?, steerState?:'queued'|'undelivered', source?, timestampMs?, attachments?:[{id,name,contentType}], audio?:{base64,mimeType,id}, toolCalls?, producedArtifactIds?, producedCallIds?, quotedContent?, smsContext?, senderLabel?, senderNumber?, emailContext?}`. Artifacts arrive separately and are paired to messages by `producedArtifactIds` / `producedCallIds` (CB 1740-1760).

**Observed: system message sources and their badges** (CB 4729-4741): `scheduled_action` "Scheduled reminder fired", `heartbeat` "Heartbeat check-in", `goal_review` "Scheduled goal review", `oauth-connected` "Account connected", `elevenlabs_postcall` "Phone call completed", `inbound_photon` "iMessage received", `inbound_email` "Email received", `inbound_alias_email` "Signup email received", `delivery_failed` "Email delivery failed", `sidebar_directive` "Instruction from a private chat", `sidebar_call_report` "Report from your agent's call". These name the channels that can inject a turn into a session: scheduler, heartbeat, goal review, OAuth callback, ElevenLabs post-call, Photon (iMessage), inbound email, alias email, and a private sidebar thread.

**Observed: tool call** (UCF 2626-2650, 4210-4215; CB 2013-2027): `{id, name, status:'running'|'done'|'failed'|'stopped', isError?, startedAtMs, displayLabel?, meta?:{family, running, done, failed}, input?:{connectorId, endpointId, serverId, toolName}, rawInput?, result?}`.

**Observed: how step labels are chosen** (CB 2032-2037). Running: `tool.meta.running ?? tool.displayLabel ?? registry.running`. Done: `tool.meta ?? registry ?? tool.displayLabel`. Fallback: humanized tool name. So the server can send a label per call and it wins over the client registry. The client registry (CB 1864-2010) covers about 95 tool names with running/done pairs, for example `web_search` "Searching the web…" / "Searched the web", `browser_use` "Operating the browser…" / "Operated the browser", `place_call` "Placing call…" / "Placed call", `wait_for_user_input` "Waiting for your reply…" / "Got your reply", `add_contact` done "Fo will remember this person", plus `run_javascript`, `search_memory`, `publish_dashboard`, `write_document`, `generate_image`, `mcp_call`, `connector_call`, `send_wajo_email`, `search_products` through `checkout_cart`, and the Gmail, Calendar, Drive, Sheets, Slides, Forms, Slack and WhatsApp tools. Families: `google | voice | calls | knowledge | operator | contacts | wajo | mcp | shopping | unknown` (CB 1838). Connector and MCP calls label as `"${name} · ${humanize(action)}"` (CB 2045). `browser_*` calls get a brand icon by sniffing `rawInput.url | domain | site` (CB 1796-1830).

**Observed: the "Completed N steps" header** (CB 9749-9753, 9871-9915): `` `Completed ${n} step|steps` `` joined with `` `${f} failed` `` and `` `${s} stopped` `` by " · "; while busy it reads `` `${n} done` ``. Running rows shimmer; settled rows stay visible for a minimum dwell of 2 s (constants 2000 and 1000 ms, CB 9803-9840); expanded view groups by family, shows 10 inline and folds the rest into "+N earlier" (CB 9707-9748). Failed calls are filtered out of the list body entirely (CB 5723-5727), and a stopped message gets an italic "(stopped)" (CB 10436). The working line, in priority order, is `message.progress`, then the running tool label, then `message.activity`, then `{working:"Thinking…", analyzing:"Looking into it…", calling:"On a call…"}` (CB 6864-6873).

**Observed: agent states and the mascot.** `agentState` in `idle, working, analyzing, calling, waiting, blocked, done, failed` (CB 9944-9958); the terminal set is `{idle, done, failed, blocked}` (UCF 164). Behind flag `fo-mascot-agent-state`, the avatar animates per state (CB 1166-1250: `calling` 2.77 s with six audio bars, `blocked` a 1.6 s spiral, `failed` X-eyes and a shake) with aria titles "Fo, waiting for you", "Fo, working", "Fo, done", "Fo, on a call", "Fo, reading", "Fo, something went wrong", "Fo, needs your input", "Fo, waiting" (CB 1553-1562). `fovatar-*.js` is a deterministic generative avatar from a name (OKLCH hue, 19 body shapes, expressions `happy, mad, sleepy, surprised`), used for non-Fo agents.

**Observed: the only page-level disclaimer** is "Wajo agents can make mistakes, so double-check." (chat 3353). There is no per-message proof line or timing footer in this build; `data-slot="message-footer"` is only a CSS hook (chat 3642). The "proof lines" in the marketing errands are static copy (section 6).

## 4. Cards: how "needs you" is drawn

The central fact: **there is no generic approve/decline card.** Consent is detected from tool results, and the user answers in the composer.

**Observed.**

- *Call consent*: `result.greenlight_verdict === "ask"` or `result.status === "consent_required"` (CB 5651-5653) puts the call card in phase `held`: pill "Needs your go-ahead", note "Waiting for your go-ahead. Nothing has been dialed." (`CallRecordingPlayer-*.js:287`, CB 6243). No button.
- *Blocked-run detection for notifications* (UCF 1557-1566): a running `wait_for_user_input` with `answer_source:'user'`, or a last tool result with `needs_credential` / `needs_connection` keys, or a status in `awaiting_approval, pending_approval, needs_payment_method, requires_action, action_required, needs_credential, verification_required, requires_setup, setup_required`. Notification titles: "<agent> needs a code | needs your approval | needs a sign-in | needs a connection"; bodies "A verification code is needed to continue." / "A purchase is waiting on your approval." / "A sign-in is waiting on you." / "An integration needs connecting."; finished: "<agent> is done" / "The run you started has finished." (UCF 1611-1642, 1736-1762). Only when the tab is not attended; chime optional; tab title gets "(N)" and `navigator.setAppBadge` (UCF 1725-1730).
- *OTP card* (CB 9318-9420): `wait_for_user_input` with `rawInput.{question, input_kind:"otp", code_length 4-12 default 6, max_wait_seconds ≤ 600, hint, answer_source}` (`workflows.calendar-*.js:84-96`) renders `<input autoComplete="one-time-code">`, "Enter" and "Cancel". Cancel sends the literal user turn "I don't have the code." (`workflows.calendar:20`). Status lines: "Code request expires in m:ss.", "Submitting code.", "Code submitted. Waiting for the agent.", "Code request cancelled. Waiting for the agent."; outcome chips "Code entered", "Cancelled", "Code request expired" (CB 9238). With `answer_source:"agent_email"` the step reads "Waiting for the verification email…", "Code received", "Verification email didn't arrive in time" (CB 2011-2027): the agent's own inbox receives OTPs.
- *Credentials never pass through chat.* Markdown links to `/v1/connector-credentials/form?connector_id=`, `/v1/site-logins/form?domain=` or `/connect/card` are rewritten into cards (CB 4849-4860): "Login Required" / "Save your ${domain} login through Wajo, outside chat." / "Save Login"; "Authentication Required" / "Enter the credential through Wajo, outside chat." / "Enter Credential"; "Connect your payment card" / "Add a payment card through Wajo, outside chat." / "Connect Card" (CB 4786-4812). The button is a plain link with `return_to` and `theme` appended (CB 5302-5320). Once the `siteLogins` query shows a login for that domain newer than the message, the card becomes "${domain} login saved" with a "Continue" button that re-sends the previous user message verbatim (CB 5325-5338; chat 3288-3292). Markdown images pointing at the `agentnet-uploads` bucket are stripped (CB 1772-1794).
- *OAuth connect card* (CB 5461-5559): "Connect ${provider}" / "Connect your ${provider} account so the agent can use it." → `useOAuthActions.mutate({providerName, sessionId, addAccount})`; completion arrives as a system message `[CONNECTED: provider]` (CB 5041).
- *Payment method needed* (CB 7055-7080): result `{status:"needs_payment_method", price_cents, credits_available_cents, card_charge_cents}` → "${credits} starter credits + ${card} card = ${total} total" and "Add payment method" → `/user/payments`.
- *Shopping*: basket item `{variant_id, shop_domain, title, price_minor, currency, quantity, image_url, added_at}`; checkout `{checkouts:[{seller, items, total_minor, currency, checkout_url, prefilled:"none|contact|shipping|full", shipping_option, merchant_messages[{code,severity,content}], error, fallback}], grand_total_minor, note}`; buy statuses `purchased | declined | handed_off | failed` (CB 7096-7215, 7270). Confirm dialog: "Buy N items for $x with your ${brand} •••• ${last4}?" / "Checkout runs separately with each seller, so this can take a moment." with an idempotent `requestId` (CB 7620-7700). Decline copy: "This purchase created a debt. Settle it before trying again." The product carousel adapter map is empty in this build (CB 8420), so the cart strip is unreachable (inferred: flag-stripped or abandoned).
- *Calls*: `place_call` takes `rawInput.recipient_name, recipient_phone` and returns `result.call_id` (CB 5655-5667). Call artifact: `{vendor_name, status, terminal_reason, call_objective, phone_number, direction, call_id, session_id, started_at, ended_at, duration_seconds, conversation_id, gcs_path, audio_gcs_path, content_type, transcript_turns[{text, role, author}]}` plus STT diagnostics `{segments[{utterance_id, text, speaker, final, committed, drop_reason, barge_in_id, observed_ms}], barge_ins[{id, source, at_ms, resolution, resolved_ms}], zero_retention}` (`artifact.schema-*.js:40-80`). Phases `dialing → failed | held | placed → completed` (CB 6244-6252); terminal reasons `hold_budget` "Ended after holding as long as allowed", `idle_silence`, `inbound_media_lost`, `realtime_recovery_exhausted` (CB 5617-5622); "Another call to this number is still in progress." (CB 5626-5633). Player has a 48-bar waveform, speeds 1 to 2x, transcript and "Download Recording" as `call-${id}.mp3`.
- *Schedule card* from `schedule_action`: `{title, status:"scheduled"|"recurring"|"already_scheduled", run_at, cron_expression, timezone}` → "Scheduled for <date>" / "Recurring: <humanized cron> (tz)" (CB 8963-9000).
- *Address* from `save_address`: `{label, first_name, last_name, line1, line2, city, region, postal_code, country, phone}` (CB 7005-7040).
- *Artifacts*: server types `generated_image, browser_screenshot, browser_download, generated_document, html_document, rendered_view, purchase_screenshot, assistant_hand_back, voice_memo` (`artifact-BwzITdAC.js:49-59`); client kinds `dashboard | call | document | file` (CB 6830-6862). HTML renders in `<iframe sandbox="">` with scripts disabled, loaded through a same-origin proxy URL, never `srcdoc` except for dashboards (`SandboxedHtmlFrame-*.js`). Dashboard spec: `{Title, Subtitle, Slug, KPIs:[{Label, Value, Delta, Trend:"up"|"down"|"flat"}], Charts:[{Type:"bar"|"line"|"area"|"pie"|"donut"|"doughnut", Title, Labels, Series:[{Name, Data}], Unit, Note}]}` (`artifact-BwzITdAC.js:20-46`). Documents share with "Only me" / "Anyone with the link" at `wajo.ai/s/…` (`ShareDocumentDialog-*.js:34-40`).

**Inferred.** Approval is a conversation, not a widget: the server emits a tool result whose status is "ask", the client renders a held card, and the user's next text turn is the approval. This keeps every decision in the transcript and makes "approved before Fo booked it" auditable from messages alone. The cost is that the client cannot tell an approval from any other reply; the server must.

## 5. Home: attention, suggestions, radar, activity

The home page lives in `chat` 2200-2940, not in `DashboardView` (that is a per-agent report dashboard with `reportKind` such as `aeo_scorecard | pipeline_health`).

**Observed.**

- Inbox item `kind` in `attention | schedule | session`; `status` in `needs_you | working | scheduled | done | didnt_finish` (chat 2234-2235, 2401, 2406). Tabs: `input` "Need your input" shows `needs_you`; `radar` "On radar" shows `scheduled`; `activity` "Last Activity" shows `done, didnt_finish, working` (chat 2249-2276). Empty copy: "Nothing needs you right now." / "When an agent gets stuck on something only you can answer, it waits for you here."; "Your agent's schedule is empty."; "Nothing finished yet." / "What your agents get done shows up here, in their own words."
- Attention kinds: `ATTENTION_KIND_PURCHASE_APPROVAL` "Purchase approval", `ATTENTION_KIND_CREDENTIAL_FIX` "Credential fix", `ATTENTION_KIND_SUGGESTED_ACTION`, anything else "Blocking question" (chat 2225-2233). Requirement badges `ATTENTION_REQUIREMENT_KIND_INFORMATION | DECISION | ACTION` → "Information needed" / "Decision needed" / "Action needed" (chat 2356-2370). Suggested actions are excluded from all tabs and counts (chat 2285-2292): they surface only as the three suggestion cards.
- Item fields: `id, title, kind, status, agentId, agentHandle, sessionId, scheduleId, category, secondary, attentionKind, attentionRequirementKind, paused, nextRunAtMs, timestampMs, outcome, failureReason` (chat 2199-2222, 2410-2421, 2479-2500). ## 10. What this changes for our plan

The ranked list in [wajo-fo.md](wajo-fo.md) stands. These are the new facts from the bundle that sharpen or add to it.

1. **Approval is a transcript turn, not a widget.** Fo has no approve/decline card: a tool result with `greenlight_verdict:"ask"` or `status:"consent_required"` draws a held card and the user's next message is the decision. We already do approvals in iMessage as replies; on the web we should keep the same shape rather than build a button, so every decision stays in the run record. Cheap.
2. **Ship a status enum, not strings.** Fo's inbox is one list with `kind ∈ attention|schedule|session` and `status ∈ needs_you|working|scheduled|done|didnt_finish`, plus `attentionKind` and `attentionRequirementKind` (information, decision, action). Our home page can be the same single query over runs, approvals and schedules. Half a day, and it also gives the daily iMessage check-in its grouping.
3. **Step labels come from the server per call.** `tool_start` carries `displayLabel` and `meta.{running, done, failed}`; the client registry is only a fallback. We should emit the label when we record the execution, not derive it in the UI. Our "named steps" item gets simpler.
4. **Resilience constants to copy.** Idle stall 30 s; 11 minutes while waiting for user input; run-open backoff 1.5 s to 8 s within 95 s on "busy"; watch backoff 1 s to 8 s with a 30 min deadline and give-up after 2 attempts with no progress; transcript reconcile every 30 s and on tab focus; a wedge probe at 120 s that trusts the server's `activeRun`. Our web training chat polls while "working" with none of this; adopt the reconcile-on-focus and the "authoritative transcript replaces local state" rule first.
5. **Steering mid-run is a first-class message state** (`steerState: queued | undelivered`). Worth adding to our run loop as "queue this for the next step" instead of rejecting input while a run is in flight.
6. **OTP is its own tool.** `wait_for_user_input` with `input_kind:"otp"`, a code length, a deadline up to 10 minutes, and `answer_source: user | agent_email`, so a verification code can be typed by the owner or read from the agent's own inbox. With AgentMail giving each of our agents an address, the `agent_email` path is one tool away.
7. **Credentials never touch the chat.** Links to credential forms are rewritten into cards whose button is a plain link with `return_to`; completion is detected by a query, and "Continue" re-sends the previous message verbatim. We have the same property through Browserbase Contexts; the "Continue re-sends the last message" trick is worth copying for site-login resumes.
8. **Heartbeats and goal reviews are system turns** (`source: heartbeat | goal_review | scheduled_action`) injected into the same session, badged in the transcript. Our planned heartbeats should post into the agent's existing thread as system messages, not open new runs.
9. **The agent is instructions + soul + voice + model + effort.** Soul sections (`identity, personality, values, operatingPrinciples`) are a reasonable schema for our "purpose and rules" training output; effort as an explicit field maps to our cheap/strong model switch.
10. **Connector builder is an agent session** (build-mcp-server returns a `sessionId` and polls `latestAssistantText`). Our planned "connector from public docs" can reuse the run loop instead of a bespoke pipeline.
11. **Money states to model if we add payments**: `autoApproveUnderCents`, `spendingPaused`, holds (`reservedAmountCents`), debt (`owedCents`, `collectibleDebtCents`) and settlement outcomes. Even without cards, `max_usd_without_asking` plus a pause flag is the minimum.
12. **Not worth copying**: Deepgram-in-browser dictation (we are iMessage-first), Live Voice as dictation-plus-TTS, the empty product-carousel path, PostHog chunk tagging.
