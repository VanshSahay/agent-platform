# Eval harnesses for tool-using agents: who does what, and what Circle should take

Researched 2026-10-19 from primary sources only: repository READMEs and source files on GitHub, the papers on arXiv, and first-party docs. Compared against what runs in `src/eval/` today and the proposal in [eval-harness.md](../eval-harness.md). Anything not confirmed at its source is marked [unverified].

## Circle's harness in one paragraph

A scenario is `setup` (seed fake hands and memories), `turns` (messages from a named person in a named room), `checks` (functions over the store). `runScenario` plays it through the real `Runtime` with any `ModelClient`, a `FakeClock` frozen at Tue 13 Oct 2026 10:00 LA, in-memory SQLite, fake hands, deliveries captured; checks read runs, tool calls (with `evidence`), run events ordered by `seq`, attention items, commitments, memories and deliveries, never the model's prose (`src/eval/harness.ts`, `world.ts`, `scenarios.ts`). Six scenarios. `bun run eval` plays them once each against the configured model and exits non-zero on any failed check (`run.ts`). `test/eval.test.ts` proves the graders with a `ScriptedModel` that behaves, one that only chats (must fail), and one that throws (reported, checks still run). One trial per scenario, fixed user turns, no timer or event turns, no category tags, no caching, no judge.

## 2. Findings per source

### τ-bench and τ²-bench (Sierra)

- World: "(a) JSON databases, (b) Python API tools, (c) Markdown domain policies, and (d) JSON task instances"; each tool "is deterministic and implemented as a Python function" ([paper §3](https://arxiv.org/html/2406.12045)).
- Reward is binary, r = r_action × r_output: "whether the final database is identical to the unique ground truth outcome database" and "whether the agent's responses to the user contain all necessary information". The authors add that r = 1 "might be a necessary but not sufficient condition" ([paper](https://arxiv.org/html/2406.12045)).
- pass^k is "the chance that all k i.i.d. task trials are successful, averaged across tasks", E_task[C(c,k)/C(n,k)], introduced because customer-service agents need reliability, not one lucky run ([paper](https://arxiv.org/html/2406.12045)). The repo leaderboard reports Pass^1 to Pass^4 ([README](https://github.com/sierra-research/tau-bench)).
- τ² grading: the target DB is built by replaying the task's `actions` on a fresh environment and the predicted DB hash is compared to it, so "any agent trajectory that produces an equivalent end state passes"; default `reward_basis` is `["DB", "COMMUNICATE"]`, `nl_assertions` is "Experimental / WIP", and action matching is only used in a few banking tasks ([docs/evaluation.md](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)).
- A correct refusal on a read-only task earns full reward with no tool calls at all: the worked airline example in the same doc. Silence-as-correct is already a graded outcome there.
- τ² user: "can take actions and call tools in addition to communicating with the agent" on a mocked phone; the `no-user` ablation hands the agent all tools and a ticket, and dual control costs ~18 points pass^1 for gpt-4.1. Each task ran four times at temperature 0 with a gpt-4.1 user ([paper](https://arxiv.org/html/2506.07982)).
- User-simulator errors were 47% of annotated airline runs and 40% retail, but only 16% in telecom, which the authors attribute to a domain that "shapes and tightly constrains user behavior through its environment" rather than prompting ([paper](https://arxiv.org/html/2506.07982)). Lesson: a scripted or state-constrained user beats a free LLM user.
- Error analysis is a separate LLM pass (`auto_error_identification.py`) that assigns fault to user, agent or environment, with the README's own warning that it "may lead to inaccurate error identifications" ([README](https://github.com/sierra-research/tau-bench)).

### ToolSandbox (Apple)

- Stateful world: settings DB, contact book, messaging DB, reminders; tools gated by cellular, wifi, location and low-battery state, with nested dependencies; "Stateful tools cover 44% of ToolSandbox toolbox" ([paper](https://arxiv.org/html/2408.04682)).
- Grading is a milestone DAG; each milestone's similarity is the geometric mean of its measures, so one zero zeroes the milestone; `guardrail_similarity` requires an exact DB match ([README](https://github.com/apple/ToolSandbox)).
- Minefields "define events that must NOT occur"; score = score_M+ × 1(score_M− = 0), so any minefield hit makes the whole trajectory 0 ([paper](https://arxiv.org/html/2408.04682)). This is Circle's "no outreach without a yes" check, generalised.
- The user simulator prompt has three parts: goal, "Knowledge Boundary, which inform the user simulator what it should and should not know", and few-shot demonstrations; `end_conversation` is the user's only tool ([paper](https://arxiv.org/html/2408.04682)).
- Scenarios carry categories (single/multiple tool call, single/multiple user turn, state dependency, canonicalization, insufficient information) and results are reported per category (Table 6). Augmentations scramble tool names and strip argument descriptions to test robustness ([README](https://github.com/apple/ToolSandbox)).

### AppWorld

- "a state-based programmatic evaluation approach": each task has expected changes and allowed changes, and the evaluator checks the DB diff contains all expected changes and nothing outside expected ∪ allowed; the abstract calls the second half "checking for unexpected changes, i.e., collateral damage" ([paper](https://arxiv.org/html/2407.18901)).
- Tests carry `no_op_fail` / `no_op_pass` labels saying whether the test fails or passes when the agent does nothing ([README](https://github.com/stonybrooknlp/appworld)). That is the metadata Circle's "chatty model must fail" test encodes by hand.
- SGC, "the percentage of task scenarios for which the agent passed all evaluation tests for all tasks from that scenario", is "a form of consistency metric" over three variants of one scenario ([paper](https://arxiv.org/html/2407.18901)).
- Each task's initial state includes "the state of the app databases and the current date and time of the task"; task DBs store only diffs from the base DB ([README](https://github.com/stonybrooknlp/appworld)).
- `appworld verify tasks` runs the gold solutions against the tests: the reference solution proves the graders ([README](https://github.com/stonybrooknlp/appworld)).

### WebArena / BrowserGym / SWE-bench / AgentBench / GAIA

- WebArena evaluators are `string_match` (exact, must_include, LLM `fuzzy_match`), `url_match`, `program_html` (navigate, locator, required contents); `EvaluatorComb` multiplies, so one miss is 0 ([evaluators.py](https://github.com/web-arena-x/webarena/blob/main/evaluation_harness/evaluators.py)). Environment reset is a documented procedure run after the full 812-task pass, not per task ([README](https://github.com/web-arena-x/webarena)).
- BrowserGym's `AbstractBrowserTask(seed)` has `setup(page) -> (goal, info)`, `validate(page, chat_messages) -> (reward, done, message, info)`, optional `cheat` (a reference solution) and `teardown` ([task.py](https://github.com/ServiceNow/BrowserGym/blob/main/browsergym/core/src/browsergym/core/task.py)).
- SWE-bench: `FULL` only when `f2p == 1 and p2p == 1`; `test_failed` treats a missing or skipped test as failed for F2P, while a skip is not a regression for P2P ([grading.py](https://github.com/SWE-bench/SWE-bench/blob/main/swebench/harness/grading.py)). Harness caches by `run_id` and `instance_id` only ([README](https://github.com/SWE-bench/SWE-bench)).
- AgentBench runs task workers in docker behind a controller and assigner; the README does not document per-environment grading ([README](https://github.com/THUDM/AgentBench)).
- GAIA: "quasi exact match", one correct answer, and an explicit rejection of model judging: "Model-based evaluations on the other hand are by construction dependent of stronger models" ([paper](https://arxiv.org/html/2311.12983)).

### Anthropic, "Demystifying evals for AI agents"

- Vocabulary: task, trial, grader, transcript, outcome ("the final state in the environment at the end of the trial") ([post](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)).
- "it's often better to grade what the agent produced, not the path it took"; strict step sequences are "too rigid". State-based example: judge a booking agent on "whether a reservation exists in the environment's SQL database".
- pass^k: 75% per trial gives about 42% at k = 3. "Each trial should be 'isolated' by starting from a clean environment." "For each task, it's useful to create a reference solution: a known working output that passes all graders."
- "20-50 simple tasks drawn from real failures is a great start." A 0% task across many trials "is most often a signal of a broken task, not an incapable agent". "Read the transcripts!" "grade each dimension with an isolated LLM-as-judge rather than using one to grade all dimensions." No first-party Claude Agent SDK eval page was found; the SDK repo only notes its end-to-end tests make real API calls [unverified beyond search].

### Inspect AI (UK AISI)

- Custom scorer: `@scorer(metrics=[accuracy(), stderr()])` on `async def score(state: TaskState, target: Target) -> Score`; grader models resolved by role (`get_model(role="grader")`); `Score` has `value`, `answer`, `explanation`, `metadata` ([custom scorers](https://inspect.aisi.org.uk/custom-scorers.html)).
- Repeats: `epochs=Epochs(5, "mode")`; reducers `mean`, `median`, `mode`, `majority`, `max`, `pass_at_{k}`, `pass_k_{k}`, `at_least_{k}`; `--epochs n` from the CLI ([metrics](https://inspect.aisi.org.uk/metrics.html)).
- Coverage: `grouped(accuracy(), "category")` over a sample `metadata` key; `stderr(cluster="category")` ([metrics](https://inspect.aisi.org.uk/metrics.html)).
- Cache key = model + base URL + message history + epoch + generate config + tools + tool_choice; default expiry one week; `CachePolicy(per_epoch=False)` to share across epochs ([caching](https://inspect.aisi.org.uk/caching.html)).
- Sandboxes: `sandbox="docker"`, per-sample compose files, per-sample `setup` bash script after `files` are copied; `sandbox().exec()` with `timeout_retry=False` for non-idempotent commands ([sandboxing](https://inspect.aisi.org.uk/sandboxing.html)).
- Scripted model: `MockLLM` takes `custom_outputs` as a list, generator or callable `(input, tools, tool_choice, config)`; exhausting a list raises `ValueError("custom_outputs ran out of values")` ([mockllm.py](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/src/inspect_ai/model/_providers/mockllm.py)). Same shape as Circle's `ScriptedModel`, including the callable form.

### LangSmith and openevals

- `create_trajectory_match_evaluator(trajectory_match_mode=…)` with `strict`, `unordered`, `subset`, `superset`; `tool_args_match_mode` and per-tool `tool_args_match_overrides` (field lists or comparator lambdas); `create_trajectory_llm_as_judge` with `TRAJECTORY_ACCURACY_PROMPT` ([README](https://github.com/langchain-ai/openevals)).
- `run_multiturn_simulation(app, user, max_turns, stopping_condition, trajectory_evaluators)`; `create_llm_simulated_user(system, model, fixed_responses)` plays fixed messages first, then lets the LLM continue; the app gets only the latest message and must keep history by `thread_id` ([README](https://github.com/langchain-ai/openevals)).
- The complex-agent tutorial grades a trajectory as a subsequence ("Check how many of the desired steps the agent took") and runs the graph with `config={"env": "test"}` so refunds are mocked ([tutorial](https://docs.langchain.com/langsmith/evaluate-complex-agent)).
- `@pytest.mark.langsmith` with `LANGSMITH_TEST_CACHE=/path` caches HTTP requests to disk ("All requests will be cached to `tests/cassettes`"), committed so CI replays; `cached_hosts=[…]` limits it ([pytest](https://docs.langchain.com/langsmith/pytest)).

### Claude Code plugin evals (`claude plugin eval`)

- Each run is "a fresh, isolated non-interactive session" in an empty workspace; "each case runs three times by default"; a case score is the mean across runs; `--threshold` (default 1.0) gates the exit code; `--max-cost-usd` caps spend ([docs](https://code.claude.com/docs/en/plugin-evals)).
- Six grader types: `regex`, `tool_used` (with `input_match`), `tool_order`, `file_exists` cost nothing; `llm` and `baseline` call a judge. "There are no custom-code graders." Advice: one grader on the result and one on the steps.
- Baseline arm: every case also runs without the plugin; `Δ` is what the plugin contributed; graders that cannot pass without the plugin are excluded from both arms as `scored: false`.
- Mock MCP servers as one Markdown file per tool: body is the tool's return with `{{input.field}}` substitution; an `expect:` block "guards the input. If a call violates it, the run aborts with score 0 and records why"; `error: true` returns a tool error; `type: agent` lets the judge answer, and its answers can be adopted into `mocks/.replay/` so "later runs answer the identical call from it with no model call".
- `tags` in `prompt.md` frontmatter and `--tag` to filter; `report.html` per run with every grader's verdict and the judge's excerpt; `--keep-temp` keeps each run's sandbox.

### Braintrust, DeepEval, promptfoo, Mastra, Letta, Vercel AI SDK

- Braintrust `trialCount` runs each input N times and "bucketing test cases with the same `input` value"; per-row override ([advanced](https://www.braintrust.dev/docs/evaluate/advanced-evaluations)). `braintrustdata/eval-action@v2` posts results to the PR; `--first N` for PR smoke tests; a reporter's `reportRun` return decides the exit code ([CI](https://www.braintrust.dev/docs/evaluate/run-in-ci)). No baseline comparison documented on that page.
- DeepEval `ToolCorrectnessMetric` compares `tools_called` to `expected_tools` deterministically, with `should_consider_ordering`, `should_exact_match`, `ToolCallParams.INPUT_PARAMETERS`; an LLM enters only when `available_tools` is given ([docs](https://deepeval.com/docs/metrics-tool-correctness)). `ConversationSimulator.simulate(conversational_goldens, max_user_simulations=10)` stops on `expected_outcome` ([docs](https://deepeval.com/docs/conversation-simulator)).
- promptfoo assertions `trajectory:tool-used`, `trajectory:tool-args-match`, `trajectory:tool-sequence`, `trajectory:step-count`, `trajectory:goal-success` (judge), plus `trace-span-count` ([assertions](https://www.promptfoo.dev/docs/configuration/expected-outputs/)). `simulated-user` provider: `instructions`, `maxTurns` (10), stop on `###STOP###`; the simulated user runs on promptfoo's hosted models unless disabled ([docs](https://www.promptfoo.dev/docs/providers/simulated-user/)).
- Mastra `createToolCallAccuracyScorerCode({ expectedTool, strictMode, expectedToolOrder })` is binary and code-only; quick checks `checks.calledTool`, `didNotCall`, `toolOrder`, `maxToolCalls`, `usedNoTools`, `noToolErrors` ([reference](https://mastra.ai/reference/evals/tool-call-accuracy), [built-ins](https://mastra.ai/docs/evals/built-in-scorers)). Live scoring samples by trace id at `sampling.rate` ([overview](https://mastra.ai/docs/evals/overview)).
- Letta evals: suite YAML with `dataset`, `target`, `graders` (`kind: tool` with `contains|exact_match|regex_match`, `kind: model_judge` with per-row `rubric`), `reward`; `num_runs`; `--cached` "Re-grade saved trajectories without re-running the target" ([README](https://github.com/letta-ai/letta-evals)).
- Vercel `MockLanguageModelV4` takes `doGenerate` as an array of results so a tool call then a final answer can be scripted; assert on `model.doGenerateCalls.length` ([testing](https://ai-sdk.dev/docs/ai-sdk-core/testing)). LangChain's `GenericFakeChatModel` is an iterator of `AIMessage | str` ([source](https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/language_models/fake_chat_models.py)).
- OpenAI: the Agents SDK documents tracing spans (`agent_span`, `generation_span`, `function_span`, `handoff_span`) and custom processors, nothing on evals ([tracing](https://openai.github.io/openai-agents-python/tracing/)); the Evals platform page says existing evals become read-only on 31 Oct 2026 and recommends Datasets ([evals](https://developers.openai.com/api/docs/guides/evals)); graders are `string_check`, `text_similarity`, `score_model`, `python`, `multi`, with tool calls graded through `sample.output_tools` ([graders](https://developers.openai.com/api/docs/guides/graders)).

### Time, schedules and silence

- Temporal: `TestWorkflowEnvironment.createTimeSkipping()`; "Timers (`sleep()` and `condition()` timeouts) are fast-forwarded except while Activities run"; `Worker.runReplayHistories` in CI and `DeterminismViolationError` when code drifts from a recorded history ([docs](https://docs.temporal.io/develop/typescript/testing-suite)). This is the only harness found that tests schedulers by moving the clock rather than waiting.
- OpenClaw heartbeat: the prompt is "sent verbatim as the scheduled user message"; the agent "reply with `NO_REPLY`" when nothing needs attention; legacy `HEARTBEAT_OK` is stripped and the reply dropped if what remains is ≤ 300 characters; `activeHours` skips ticks ([heartbeat](https://docs.openclaw.ai/gateway/heartbeat)). Cron delivery: "`NO_REPLY` suppresses a text-only announcement without failing the run"; `none` delivery; auto-disable after 10 consecutive failures ([delivery](https://docs.openclaw.ai/automation/cron-jobs/delivery)). No test harness documented.
- Hermes cron: LLM jobs "reply exactly `[SILENT]`"; script-only jobs stay silent on empty stdout or `{"wakeAgent": false}`; monitors skip the agent when output is unchanged ([docs](https://hermes-agent.nousresearch.com/docs/plugins/hermes-cron)). No harness; the troubleshooting guide warns the marker can swallow real replies [from search summary, unverified at page].
- Supermemory's Instinct post is about memory storage (git-tracked markdown, grep), not evaluation; nothing on heartbeats or a harness ([post](https://supermemory.ai/blog/reverse-engineering-instinct-memory/)).
- Both always-on products grade silence by a sentinel string in model text. Circle forbids exactly that (footers and outcomes come from records, `CLAUDE.md`); `stay_quiet` as a recorded tool call is the stronger design and nobody surveyed has it.

### Fakes, cassettes and replay

- VCR.py record modes: `once` (replay, error on a new request when a cassette exists), `new_episodes`, `none` ("Cause an error to be raised for any new requests"), `all` ([usage](https://vcrpy.readthedocs.io/en/latest/usage.html)). LangSmith's test cache and Inspect's cache are the same idea applied to model calls; plugin evals' `.replay/` applies it to agent-played mock tools.
- τ² replays gold `actions` on a fresh environment to compute the target state, so the fixture is a tool trace, not a hand-written DB ([docs](https://github.com/sierra-research/tau2-bench/blob/main/docs/evaluation.md)).

## 3. Where Circle already matches

- **State-based, outcome grading.** Checks read the store and event order, never prose; τ, AppWorld, Inspect scorers and the Anthropic post all recommend this. Circle's "evidence on the tool record" is stricter than τ's DB hash because it also proves the side effect happened through a gate.
- **Isolated world per trial.** `evalWorld()` builds a fresh app, store and clock per scenario, like AppWorld's per-task DB and Inspect's per-sample sandbox.
- **Minefields.** "No outreach with evidence", "no community post without a yes", "nothing private delivered to the room" are ToolSandbox minefields and AppWorld collateral checks, written per scenario.
- **Scripted model proves the graders.** `ScriptedModel((req) => …)` is Inspect's `MockLLM(custom_outputs=callable)` and Vercel's `MockLanguageModelV4`; the "chatty model fails" test is AppWorld's `no_op_fail` idea.
- **Fake tools with seeded answers.** `FakeSearch`, `FakePhone`, `FakeCommunity` closures are τ's deterministic Python tools and plugin evals' mock files.
- **Error reported, checks still run; non-zero exit; `--only`.** Same as `claude plugin eval` and Braintrust CI.
- **Silence is a recorded outcome.** `stay_quiet` is a tool call and quiet runs are stored; ahead of OpenClaw and Hermes.

## 5. What to take, ranked by value over effort

1. **Trials and pass^k.** `--trials k` in `run.ts` plays each scenario k times on fresh worlds; report per-scenario pass count, per-check pass rate, and pass^k (τ-bench formula). Gate on all-k by default, `--threshold` to loosen. Half a day.
2. **Store diff as a standard check.** Snapshot counts and ids (memories by scope, commitments, schedules, attention items, evidenced side-effect calls by tool) before `turns`, diff after; a scenario declares `expects: { commitments: 1, schedules: 0, outreach: [] }` and anything outside it fails. One generic check appended to every scenario (AppWorld's rule). Half a day.
3. **Reference script and do-nothing model for every scenario.** The proposal's "script per scenario", plus: run the chatty model over all scenarios in `bun test` and assert each fails; each check gets `noOpPasses: true|false` so the harness can verify the label (AppWorld `no_op_fail`). A day, mostly writing scripts.
4. **Tick and event turns.** As proposed, with the grader for quiet: a run with trigger timer or event exists, has a `stay_quiet` tool call, and no delivery to any room. Temporal's time-skipping is the model; Circle's `FakeClock.tick` and a scheduler tick entry point are already there. Half a day plus the three proposed scenarios.
5. **Tags and grouped output.** `category`, `shape`, `cases` on scenarios; `--category`, `--list`; pass rate per category and the uncovered list, Inspect's `grouped`. Two hours.
6. **Check helpers.** `called(name, { min, evidence })`, `never(name, { evidence })`, `order(a, b)`, `afterGate(name)` over the existing `toolCalls`/`events` helpers in `scenarios.ts`; rewrite the six scenarios on them. Half a day; pays back on every new scenario.
7. **Input guards on presets.** Named presets (`oneRepairer`, `noAnswer`, `emptyWeb`, `shop`) whose fakes record every input and can `expect` shapes; a violation fails the scenario with the input recorded (plugin evals `expect:`). Two hours.
8. **Cassette model.** `CassetteModel(inner, path, mode)` keyed by a hash of `{model, system, messages, tools}`; `record` on `bun run eval --record`, `replay` in `bun test` with `none` semantics. Gives an offline test on a real GLM transcript and flags prompt drift. One day. Do after 1 to 3; it only pays off once the suite is stable.
9. **Report and cost ceiling.** `--report <dir>` writes one Markdown file per scenario per trial (turns, tool calls, deliveries, failed checks); `--max-tokens` stops starting new trials past a budget (the $5/day cap). Three hours.
10. **Baseline arm.** `--no-skills` plays the suite with the skills index empty and prints Δ per category. Two hours, once 5 exists.
11. **Persona member for card answers.** An openevals-style `fixed_responses`-then-LLM member, used only for scenarios where the right answer depends on the question the agent asked. Keep fixed turns everywhere else: τ² found free LLM users wrong in 40 to 47% of runs. Half a day; later.

Not worth taking: an LLM judge in the pass/fail gate (GAIA rejects it, τ² marks it experimental, Anthropic says calibrate it against humans first); strict trajectory match as the primary grade (Anthropic: "too rigid"); sentinel strings for silence (OpenClaw, Hermes); docker sandboxes (Circle's hands are in-process fakes and the world is one SQLite file).

## 6. Verdict on docs/eval-harness.md

**Keep.** Tags with category, shape and cases (§3.1); tick and event turns (§3.2); a well-behaved script per scenario run offline (§3.3); named presets (§3.4); coverage output (§3.5); the nine new scenarios and the rule that every check reads the store. The quiet-run grading in scenario 8 (quiet status, `stay_quiet` call, no reply event) is the right shape and better than anything surveyed.

**Change.**
- §3.3: the offline test should also play the do-nothing model against every scenario and assert at least one check fails per scenario; add `noOpPasses` to `Check` so the harness can confirm the label.
- §6 cost: budget for k trials, not one. Three trials on 15 scenarios at 15 to 25 turns is roughly 1,000 GLM turns; `--category` and `--trials 1` for iteration, full k on merge.
- The checks table (§4) lists positives and per-scenario negatives; add the generic store-diff check to every row so "nothing else changed" is not re-derived by hand.

**Add.** `--trials k` with pass^k (take 1); the store diff (take 2); check helpers (take 6) before writing nine more scenarios by hand; input guards on presets (take 7); a report directory for reading transcripts (take 9). Defer the cassette model and baseline arm until the suite is stable.
